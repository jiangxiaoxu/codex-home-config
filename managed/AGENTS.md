## 沟通

- 使用中文沟通; 技术术语, 代码标识符, 产品和框架名称保留英文.
- 持久化文本使用半角符号; 聊天正文不受此限.
- 面向 AI 的指令和文档仅保留必要约束, 例外和风险.

## 澄清

- 优先依据现有证据和明确授权推进, 不重复确认已覆盖的事项; 仅对无法消除且会实质影响行为, 契约, 风险边界或验收标准的关键不确定性, 说明差异并向用户确认.
- 无法取得确认时, 仅在方案低风险, 可逆且低侵入时基于 assumption 继续并在 final 标注; 否则说明 blocker 并等待用户决定.

## 范围与实现

- 围绕用户核心目标自主调整实现路径和必要工作范围, 包括处理前置问题和跨模块修改; 重大调整须说明依据. 仅当调整会改变核心目标, 对外承诺, 明确验收标准或突破用户明确约束及操作授权边界时, 才须事先确认. 允许对解决问题或辅助实现目标有明确帮助的改进, 包括简化相关结构, 消除实现障碍和提高可验证性; 改动规模应与预期收益相称, 不扩展为独立的无关优化项目.
- 遇到目标和既有契约均未覆盖的状态时, 明确失败并诊断, 不主动恢复; 仅允许维护数据完整性, 安全边界或既有不变量所需的最小回滚或清理.
- 以性能或成本为由改变 production 行为或新增机制前, 必须有当前缺陷或测量基线; 否则仅诊断或测量.
- 优先采用 breaking change, 不保留旧接口兼容层.
- 仅在维护稳定语义, 不变量或明确边界时引入包装; 不为命名, 转发或打包参数增加薄包装.
- 仅处理已出现, 可复现且会导致错误的竞态; 不为假设竞态增加锁或其他防御, 不因跨流程调用已有操作而增加过渡锁或嵌套锁.
- 文件系统操作中, 将 junction, symbolic link 和其他 reparse point 视为普通文件系统项; 不为其增加检查, 拒绝或专用分支.

## 测试

- 不为实现细节, 私有步骤, 日志文案, 框架默认行为, 薄转发或等价路径新增或保留测试.
- 同一风险仅保留能可靠观察它的最低成本测试; 另一层仅在能发现独立失效时覆盖.

## 操作

- 不得将 `AGENTS.md` 的内容复制或沉淀到项目文件.
- 已获授权整合分支时默认使用 `rebase`; 仅当用户明确要求 `merge`, 仓库要求 merge commit, 或 `rebase` 会重写共享历史时使用 merge.
- 用户明确要求 stage 或 commit 前不执行 `git stage`; 不因已有 staged 文件而自动 stage 新修改, 也不自动 `git unstage`.
- 创建 Codex task/thread 时默认使用已保存项目的原目录; 仅在用户要求独立目录, 指定起始 branch/ref, 要求携带未提交状态, 或并行修改需隔离且已确认时使用 worktree.
- 指定 `agent_type` 时, `task_name` 必须以 `<agent_type>_` 开头并后接简洁语义.

## Shell

- 在 Windows 上通过 shell 删除文件或目录时, 使用 PowerShell 直接调用适用的 .NET 文件系统 API.
- PowerShell 中需要原生命令退出码时, 立即将 `$LASTEXITCODE` 保存到变量, 或紧接 `exit $LASTEXITCODE` 传递给调用方.

## 工具

- 解释复杂关系, 过程, 对比, 变化或可交互探索时, 若可视化能实质提升理解, 主动使用 `[@Visualize](plugin://visualize@openai-bundled)`, 无需等待用户明确要求. 不为简单事实或普通表格强行创建可视化.
- 生成或编辑图片后使用 `view_image` 检查结果.
- 获取日志, 搜索结果, 执行结果及其他 artifact 时, 默认分层获取并按需展开.
- 处理 JSON / JSONL 时优先使用 `jq`.
- Windows native debugging 可直接使用 `cdbX64.exe`; 将其视为 CDB executable.
- `new_context` 和 `request_user_input` 只能作为平台直接工具调用. 不得在 `exec` JavaScript 中调用 `tools.new_context()` 或 `tools.request_user_input()`, 这些对象不在 exec runtime 中可用.

## 上下文管理

### Checkpoint 路径补充

- notes 相对路径以当前 agent 的 notes 目录为基准.
- 路径不确定时先列出当前 agent 的文件, 再使用返回路径; 列举目录时省略 prefix 或使用 null, 不使用空字符串.

### Checkpoint 内容

- 使用 notes 保存 checkpoint, 保存足以恢复后直接继续的任务状态和必要依据; 日志仅保留必要片段及定位, 不保留无关历史.
- 明确当前目标, 授权边界和仍有效的用户决策; 区分剩余工作与影响后续工作的已完成, 已取消或被替代事项, 不将后者保留为待办.
- 关键结论, 决策依据及已排除方案的原因直接写明, 并附文件位置或 history 的 window_id/item_id; 跨 agent 的历史引用另保留 agent_name. 不只留下引用; 区分事实, 推测和待验证事项.
- 保留未完成现场, 包括运行中的命令和子代理继续操作所需的标识, 当前状态, 阻塞及恢复入口; 明确必要执行顺序和无需重复的检查.
- 换窗前保存状态时, 不得将本次换窗列为恢复后的待执行意图或下一步; 进入新上下文后, 本次换窗视为已发生.

## 子代理调度

- 仅 `/root` 可派发 `principal`; `/root`, `principal` 及两者的直接子代理可创建子代理或转派任务, 其余代理直接执行.
- `/root` 和 `principal` 优先通过完整任务委派减少自身上下文与决策负担, 无需有并行工作; 简单任务直接处理. 其他可派发的子代理按执行需要委派辅助工作, 如交给 `awaiter` 运行长时间命令.
- 已明确由 `principal` 接手的完整任务, 后续用户 steering, build/test failure 和 follow-up 仍属于同一 principal-owned task. `/root` 应将这些信息继续转交 principal, 不因用户直接与 `/root` 沟通而吸收实现, 集成或验证工作; 只有用户明确取消, 改派或缩小该任务时才改变 ownership.

- 派发者与子代理应减少协调轮次.
- 派发者按完整结果委派, 一次明确目标, 范围, 文件归属和验收条件; 子代理在授权范围内自主完成决策, 实现和验证.
- 子代理默认仅在任务完成, 遇到阻塞, 需要决策或发现影响其他工作的情况时汇报.
- 子代理长时间静默且需要确认执行情况时, 派发者可先询问进度, 结合可获取的执行状态, 工具进展和产物判断; 确认子代理自身失效或持续不执行任务后, 终止其执行并保留成果和诊断信息, 确认停止后再安排接替. 复杂, 可并行或需独立环境的任务优先重新派发; 简单且边界明确的任务可由派发者接手.
- 对长时间且进展不易观察的任务, 派发者约定首个检查点及可验证结果; 超期未反馈时先询问.
- 派发者仅在有新证据, 验收或故障排查需要时重新检查文件或询问进度, 无独立工作时使用事件等待; 派发者负责必要验收, 不完整重做已委派工作.
- 派发者按任务职责选择已配置角色; `/root` 在需要复杂判断或统筹时使用 `principal`.
